# HookLens 공부 노트

1차 MVP를 만들면서 배운 것과 결정한 이유를 정리한 문서. 면접 준비용.
(최종 갱신: 프론트 MVP 완료 시점 — 백엔드 P0 전부 + React 화면)

## 1. 무엇을 만드나

**웹훅을 받아 주는 "임시 우체통".**

> 외부 서비스가 보내는 알림(웹훅)을 대신 받아서, 실시간으로 보여 주고, 원하는 대답을 돌려주는 개발 도구.
> 비슷한 실제 서비스: webhook.site, RequestBin

### 이야기로 이해하기
쇼핑몰 개발자가 토스페이먼츠 결제를 붙인다고 하자.
```
고객 → 토스에서 카드 결제 → 결제 완료!
                               ↓
              토스가 "○○ 주문 결제됐어요"라고 우리 서버에 알려 줌 (= 웹훅)
                               ↓
              우리 서버는 그 알림을 받고 "주문 상태: 결제 완료"로 바꿈
```
**웹훅** = "무슨 일이 생기면 그쪽에서 먼저 알려 주는 것". 택배 비유로, 웹훅이 없으면 1분마다 현관문을 열어 보고(폴링), 있으면 택배 기사가 초인종을 눌러 준다.

이 "알림을 받아 처리하는 코드"를 짤 때 개발자가 막히는 순간들:

| 막히는 순간 | HookLens로 해결 |
| --- | --- |
| 😵 토스가 정확히 어떤 모양으로 보내는지 모르겠다 | 📮 받은 알림을 **있는 그대로 전부**(주소·헤더·바디) 보여 준다 |
| 😵 내 컴퓨터(localhost)로는 알림이 안 온다 (토스는 인터넷에 있고, 내 노트북은 인터넷에서 안 보인다) | 📮 **인터넷 주소**를 하나 만들어 준다. 그걸 토스에 넣으면 된다 |
| 😵 우리 서버가 고장 나면 토스는 어떻게 하지? (돈은 나갔는데 주문은 안 된 상태가 되면 큰일) | 📮 "실패라고 대답해", "3초 늦게 대답해"를 **설정**해서 토스가 다시 보내는지(재시도) 미리 본다 |

### 실제 사용 예 (배포 후): 깃허브 웹훅
1. HookLens에서 **엔드포인트 만들기** → `http://서버주소/h/Ab12Cd34Ef` 주소 발급 → **복사**
2. 깃허브 저장소 → Settings → Webhooks → Add webhook → 주소 붙여 넣기
3. 그 저장소에 push → HookLens 화면에 깃허브가 보낸 알림(누가, 어떤 커밋을, 언제)이 바로 뜬다
4. 응답 설정을 500으로 바꾸면 깃허브가 "전달 실패"로 표시하는 것도 볼 수 있다

로컬에서는 외부 서비스가 내 컴퓨터에 닿을 수 없어서, 터미널로 알림을 흉내 내 보냈다(PowerShell `Invoke-RestMethod`).
그래서 배포가 중요하다 — 인터넷 주소가 생겨야 진짜 알림을 받을 수 있다.

### 좋은 점
- **쓰는 사람**: 실시간 표시(새로고침 없이), 있는 그대로 보기(문서와 실제 차이 발견), 대답 바꾸기(실패·지연 테스트), 가입 없이 버튼 한 번(24시간 뒤 자동 만료)
- **포트폴리오**: 작지만 실무에서 진짜 고민하는 문제가 다 들어 있다 — 실시간(SSE·재연결), 보안(토큰 해시·IDOR·헤더 주입), 동시성·성능(가상 스레드·DB 커넥션·커서 페이징), 테스트(실제 MySQL 통합 테스트·E2E). "왜 이렇게 만들었는지" 설명할 거리가 많다.

## 3. 기능별 정리

### ① 엔드포인트 발급 (REQ-EP-001)
- **slug**: 영숫자 10자 랜덤 주소. 경우의 수 62¹⁰ ≈ 8×10¹⁷이라 추측 불가. `Random`이 아니라 `SecureRandom` 사용(`Random`은 다음 값 예측 가능).
- **익명 토큰**: 로그인 없이 "이 우체통 주인은 나"를 증명하는 열쇠. 처음 한 번만 보여 주고 DB에는 SHA-256 해시만 저장.
- 숫자 id 대신 slug만 외부에 노출 → 순번이면 남의 엔드포인트를 추측할 수 있음.
- slug 중복은 "미리 확인 후 최대 3번 재시도" + "DB 유니크 제약" 두 겹으로 막는다.

### ② 만료 (REQ-EP-002)
- `Endpoint.isExpired(now)`: 만료 판단을 엔티티가 스스로 한다 → 규칙이 데이터 옆에 있어 여러 곳에 중복 구현되지 않음.
- 요청 시점에 판단 → 스케줄러가 "만료됨" 상태를 표시하는 방식보다 반영이 늦지 않고 컬럼도 덜 필요.
- 없는 주소는 404, 만료된 주소는 410.

### ③ 웹훅 수신·저장 (REQ-HOOK-001)
- `/h/{slug}/**`: 모든 메서드, 모든 하위 경로를 받는다.
- 메서드·경로·쿼리·헤더·바디·IP·시각을 가공하지 않고 그대로 저장 (디버깅 도구라 "받은 그대로"가 핵심).
- 바디는 한 번만 읽을 수 있는 스트림 → 원본 바이트를 직접 읽는다. 같은 이유로 `FormContentFilter`를 껐다(켜면 PUT 폼 바디가 비어 저장됨).
- 한계: 바이너리 바디는 UTF-8 문자열로 저장해 깨질 수 있음. IP는 배포 시 Nginx 뒤 실제 IP 처리 필요.

### ④ 설정된 응답 (REQ-HOOK-002)
```
컨트롤러: 요청 받음
  └ 서비스(@Transactional): 엔드포인트 확인 → 로그 저장 → 기본 규칙 조회 → 트랜잭션 끝(커밋)
컨트롤러: 규칙에 지연이 있으면 기다림 (가상 스레드)
  └ HookResponseBuilder: 규칙 있으면 규칙대로 / 없으면 200 {"ok":true}
```
- 응답 헤더 JSON은 `{"이름": "값"}` (요청 로그는 `{"이름": ["값"]}`). 사용자가 직접 입력하는 값이라 단순하게.
- `Content-Length`, `Transfer-Encoding` 같은 전송 제어 헤더는 무시.

### ⑤ 요청 목록 (REQ-LOG-002)
**주인 확인** — `EndpointService.getOwnedBySlug(slug, token)`, 이후 모든 관리 API가 재사용
```
토큰이 없다         → 401 UNAUTHORIZED     ("누구세요?")
엔드포인트가 없다    → 404 / 만료면 410
토큰 해시가 다르다   → 403 FORBIDDEN        ("당신 것이 아니에요")
```
- 해시 비교는 `equals`가 아니라 `MessageDigest.isEqual` → 항상 끝까지 비교해 타이밍 공격 방지.

**커서 페이징** — `RequestLogService.getPage`
```
요청: size=20, cursor=81
SQL:  WHERE endpoint_id = ? AND request_id < 81 ORDER BY request_id DESC LIMIT 21
결과: 21개면 → 20개만 주고 nextCursor = 20번째 id / 20개 이하면 → nextCursor = null
```
- 오프셋 대신 커서: 보는 중에 새 웹훅이 들어와도 페이지가 밀리지 않고(중복·누락 없음), 뒤 페이지도 인덱스로 바로 찾아 빠르다.
- size+1개 조회: COUNT 쿼리 없이 다음 페이지 여부를 안다.
- `Pageable`(OFFSET) 대신 `Limit`. 첫 페이지는 cursor = `Long.MAX_VALUE`.
- `size=0`, `cursor=abc`가 500이 되지 않게 `HandlerMethodValidationException`·`MethodArgumentTypeMismatchException`을 400으로 처리.

### ⑥ 요청 상세 (REQ-LOG-003)
**IDOR 방어** — `findByIdAndEndpointId`
```
공격: 내 slug + 내 토큰으로 /requests/999 (999번은 남의 로그)
  getOwnedBySlug → 통과 (slug는 내 것)  ← 이것만으로는 못 막는다
  findByIdAndEndpointId(999, 내 엔드포인트 id) → 결과 없음 → 404
```
- 남의 것도 403이 아니라 404 → 존재 여부 자체를 숨긴다.
- 조건을 자바 코드가 아니라 쿼리에 넣어, 남의 데이터는 애초에 조회되지 않게 한다.

**DTO와 record**
- 엔티티(DB 모양)를 그대로 내보내지 않고 DTO(화면 모양)로: 헤더 문자열 → 객체, 시간에 +09:00, LAZY 필드 오류 방지, API 모양 고정.
- DTO는 값만 담는 상자라 `record`(생성자·getter·equals 자동, 불변). 엔티티는 JPA가 빈 생성자로 만든 뒤 값을 채워야 해서 record 불가.
- record 생성자는 필드 순서 그대로 받는다. 같은 타입끼리 순서가 바뀌면 컴파일러가 못 잡는다 → 테스트가 잡는다.

### ⑦ 실시간 반영 (REQ-LOG-001, SSE)
```
웹훅 도착 → HookReceiveService (트랜잭션)
              ├ 로그 저장
              ├ publishEvent(RequestReceivedEvent) ──┐ (Spring이 들고 있음)
              └ 규칙 조회                              │
            커밋 성공 ─────────────────────────────────┘──▶ RequestReceivedListener(AFTER_COMMIT)
                                                            └▶ RequestStreamRegistry.send ──▶ 화면들
```
- **SSE**: 끊지 않은 HTTP 응답 하나로 서버 → 화면 방향 메시지를 계속 흘려보낸다(`event: request` / `data: {...}` / 빈 줄). 폴링(낭비·지연)·WebSocket(양방향은 불필요)보다 딱 필요한 만큼.
- **AFTER_COMMIT 리스너**: 커밋 전에 알리면 화면이 바로 상세를 조회했을 때 404, 롤백되면 유령 알림 → 커밋 후에만 보낸다.
- **이벤트로 분리**: 수신 코드는 SSE를 모른다. 서버를 늘려 Redis Pub/Sub로 바꿔도 수신 코드는 그대로.
- **Registry**: 엔드포인트 id → 연결 Set(ConcurrentHashMap, 서버 1대 메모리). 등록은 `compute`로 한 번에, Set은 `newKeySet()`이라 돌면서 지워도 안전.
- **하트비트**: 30초마다 `: heartbeat` 주석 → Nginx가 조용한 연결을 60초에 끊는 걸 막고, 실패하면 떠난 화면을 정리.
- **open-in-view: false** 덕분에 30분짜리 연결이 DB 커넥션을 붙잡지 않는다.

### ⑧ 응답 설정 (REQ-RES-001)
- **PUT + upsert**: 엔드포인트마다 기본 응답은 하나 → 통째로 바꾸기. 있으면 `update()`(변경 감지로 UPDATE), 없으면 INSERT. 같은 요청을 반복해도 규칙은 1개(멱등).
- **헤더 주입(HTTP 응답 분할) 방지**: 사용자가 넣은 헤더가 웹훅 응답에 그대로 나간다. 값에 `\r\n`이 있으면 `Set-Cookie` 같은 헤더를 끼워 넣을 수 있다 → 이름은 허용 문자 정규식(화이트리스트), 값은 줄바꿈 금지.
- 설정 전 GET은 404 대신 실제로 나가는 기본 응답 + `custom: false` → 화면 폼에 바로 채운다.
- `@Valid`를 빼먹으면 DTO의 `@Min`·`@Max`가 아예 동작하지 않는다.

### ⑨ 프론트 (React 19 + Vite 8 + Tailwind 4)
- **Vite 프록시**: 브라우저는 5173에만 요청, Vite가 `/api`·`/h`를 백엔드로 넘긴다 → CORS 설정 불필요(운영은 Nginx가 같은 역할).
- **axios 응답 인터셉터**: `{success, data, error}`를 한 곳에서 풀어 컴포넌트는 data만 받고, 실패하면 서버의 `error.message`를 받는다.
- **fetch로 SSE 받기** (`useRequestStream`): EventSource는 헤더를 못 보내서 fetch를 쓴다. 대신 직접 한다 —
  받은 조각을 버퍼에 모아 줄로 자르고(마지막 덜 온 조각은 다음으로), 빈 줄에서 메시지 하나 완성, `:` 줄(하트비트)은 무시.
  끊기면 3초 뒤 재연결 + 놓친 요청은 목록 API로 보충. 화면을 떠나면 `AbortController.abort()`로 연결을 끊는다.
- **콜백을 useRef에**: 렌더링마다 새로 만들어지는 콜백을 effect 의존성에 넣으면 매번 재연결된다.
- **merge**: SSE와 목록 API 결과가 겹칠 수 있어 requestId로 중복 제거·정렬.
- **XSS**: 토큰을 localStorage에 두므로 사용자 데이터(바디·헤더)는 글자로만 출력(React 이스케이프, dangerouslySetInnerHTML 금지).

## 4. 개념 사전

| 용어 | 쉬운 설명 |
| --- | --- |
| 엔티티 (`Endpoint`, `ResponseRule`) | DB 테이블 한 줄을 자바 객체로 표현한 것 |
| Repository | DB 창구. 메서드 이름만 쓰면 Spring이 SQL을 만들어 줌 (`findByEndpointIdAndIsDefaultTrue`) |
| Service | 실제 업무 로직 (확인 → 저장 → 조회) |
| Controller | HTTP 요청을 받고 응답을 돌려주는 입구 |
| `@Transactional` | 안의 DB 작업을 한 묶음으로 처리. 중간에 실패하면 전부 취소(롤백) |
| 생성자 주입 | `final` 필드 + `@RequiredArgsConstructor` → Spring이 필요한 객체를 넣어 줌. 바뀌지 않고 테스트에서 갈아 끼우기 쉬움 |
| `Optional` | "값이 없을 수도 있음"을 타입으로 알림 → null 실수 방지. 반환값에만 쓰고 파라미터로는 받지 않는다 |
| `map` / `orElseGet` | 값이 있으면 변환, 없으면 대체값. `orElse`는 값이 있어도 괄호 안을 먼저 실행하므로 `orElseGet` |
| `LAZY` 로딩 | 연관 객체는 실제로 쓸 때 불러옴. `open-in-view: false`라 트랜잭션이 끝난 뒤 접근하면 `LazyInitializationException` |
| `Clock` 빈 | 현재 시각을 한 곳에서 받음 → 테스트에서 시간 고정 가능 |
| 가상 스레드 | 기다리는 동안 OS 스레드를 놓아주는 가벼운 스레드 (식당 직원이 메모만 남기고 다른 테이블로 가는 비유) |
| Testcontainers | 테스트 때 진짜 MySQL을 Docker로 잠깐 띄워 검증 |
| Spring Data 메서드 이름 | getter가 아니라 **필드 이름** 기준으로 해석 (`isDefault` 필드 → `IsDefaultTrue`) |

## 5. 면접에서 설명할 결정들

1. **토큰 해시가 왜 BCrypt가 아니라 SHA-256?**
   BCrypt는 추측하기 쉬운 비밀번호를 일부러 느리게 만들어 막는 용도. 이 토큰은 32바이트 난수라 무차별 대입이 불가능하므로 빠른 해시로 충분하고, 같은 값이면 해시도 같아 바로 조회할 수 있다.
2. **지연을 왜 트랜잭션 밖에서 기다리나?**
   안에서 5초씩 기다리면 DB 커넥션(HikariCP 기본 10개)을 붙잡는다. 지연 요청 10개면 다른 요청까지 전부 멈춘다. 밖에서 기다리면 로그도 바로 보인다.
   → 이를 증명하는 테스트: "지연 응답을 기다리는 동안에도 로그는 이미 저장돼 있다".
3. **왜 가상 스레드?**
   대안: 그냥 `sleep`(톰캣 스레드 200개가 묶임), `DeferredResult` 비동기(코드 복잡). 가상 스레드는 코드는 단순한 `sleep`인데 기다리는 동안 OS 스레드를 놓아준다. 주의점(pinning: `synchronized` 안에서 기다리면 이점이 사라짐)은 우리 코드에 해당 없음(MySQL 드라이버 9.x도 해결됨).
4. **`Content-Length` 같은 헤더를 왜 막았나?**
   실제 바디 길이와 다르면 클라이언트가 응답을 끝까지 못 읽거나 잘린다. 서버가 직접 계산하게 둔다.
5. **`InterruptedException`을 잡으면 왜 `interrupt()`를 다시 부르나?**
   예외를 잡으면 중단 신호가 지워진다. 다시 살려 둬야 위쪽(톰캣)이 종료 중임을 알 수 있다.
6. **테스트를 왜 진짜 MySQL로?**
   H2 같은 인메모리 DB는 MySQL과 문법·동작이 달라 운영에서만 터지는 버그를 놓친다.
7. **SSE 인증은? (REQ-LOG-001 예정)**
   `EventSource`는 커스텀 헤더를 못 보낸다 → `fetch` 스트림으로 연결해 `X-Anonymous-Token` 헤더 인증을 그대로 쓴다. 쿼리 파라미터는 토큰이 Nginx 로그·브라우저 기록에 남고, 일회용 티켓은 저장소·재연결 처리가 필요하다.

8. **401과 403의 차이는?**
   401은 인증 정보가 없음(누군지 모름), 403은 인증은 됐지만 권한 없음. 토큰이 없으면 401, 남의 토큰이면 403.
9. **커서 페이징을 왜 썼나?**
   새 웹훅이 계속 들어오는 서비스라 오프셋은 페이지가 밀려 중복·누락이 생기고, 뒤로 갈수록 느리다. size+1개 조회로 COUNT 없이 다음 페이지를 판단한다.
10. **IDOR을 어떻게 막았나?**
    주인 확인은 "slug가 내 것인가"만 본다. 요청 id는 "id + 내 엔드포인트" 조건으로 쿼리해서 남의 것은 조회조차 안 되게 했고, 존재 여부를 숨기려고 404로 응답한다.

## 6. 작업 방식
- **브랜치 → 커밋 → PR → merge**: 기능 하나마다 브랜치, PR로 main에 합친다.
- **CLAUDE.md**: 규칙과 진행 상황. 새 세션에서도 이걸 읽고 이어간다.
- **`.env`**: 비밀 값은 여기에만. Git에 올리지 않는다.
- **`.gitattributes`**: 줄바꿈을 LF로 고정 → Windows에서 커밋해도 리눅스 CI에서 `gradlew`가 돈다.
